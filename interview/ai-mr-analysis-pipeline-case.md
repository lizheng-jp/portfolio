# AI-Based Merge Request Analysis Pipeline Optimization

## 案例定位

这是一个适合用于以下面试维度的 Engineering Case Study：

- Cost optimization
- Reliability engineering
- LLM / GenAI system design
- Trade-off and decision making
- Iterative problem solving
- Asynchronous processing and fallback design
- Evidence-based validation

对外标题：

> AI-Based Merge Request Analysis Pipeline Optimization

对外副标题：

> Reducing cost and timeout risk with an asynchronous analysis architecture

## 事实基线

### 背景

- 系统需要使用 Gemini 对用户指定时期内的 Merge Request（MR）逐一进行 AI 分析。
- 分析结果会参与后续评分，因此评价流程开始时必须能够取得所需结果。
- 最初使用 Standard API，通过同步 HTTP 请求等待模型返回。
- 在一次会议中，部门负责人提出了降低 API 成本的要求。
- 面试时可表述为「管理层提出成本优化要求」，不需要说明具体职级、公司名或内部系统名。

### 已验证的事实

- 多个 MR 合并到一个 Standard API 请求后，输入规模和指令复杂度增加，Gemini 响应变慢，最终出现 HTTP timeout。
- 改为 Batch API 后，原来由长时间同步等待造成的 HTTP timeout 在实际测试中已经完全消失。
- Batch API 内仍然保持一个 MR 对应一次独立的模型分析，而不是把多个 MR 合并进同一个分析上下文。
- 当前设计保留 Standard API。当用户选择的 MR 尚未被预分析时，系统使用 Standard API 实时取得结果，以便继续后续评分。

### 设计判断，但尚未完成量化验证

- 一个 MR 对应一次独立分析，可以减少 MR 之间的上下文干扰，因此更有利于维持分析精度。
- 在精度对比实验完成前，不应表述为「精度已经提高」或「一定更准确」。
- Batch API 的官方单价约为 Standard API 的一半，但这不等于系统的实际总成本已经下降 50%。

### 仍在验证

- 实际总成本降低了多少。
- 哪类项目和 MR 分布能够代表整体工作负载。
- 独立 MR 分析与多 MR 合并分析之间的精度差异。
- Standard API fallback 的实际触发比例。
- Batch 任务最合适的执行频率。

## 问题与方案演进

### 1. 初始方案：Standard API 同步分析

用户选择一个时期后，系统需要分析其中的多个 MR。最初采用 Standard API，通过同步 HTTP 请求等待分析结果。

管理层提出降低成本的要求后，首先考虑通过减少 API 请求次数来降低成本。

### 2. 第一轮尝试：一个请求合并多个 MR

将多个 MR 放入一个 Standard API 请求中统一分析。

出现的问题：

- 输入 token 数增加。
- 同一个 prompt 需要区分和分析多个 MR，指令复杂度提高。
- Gemini 处理时间变长。
- 同步 HTTP 请求需要持续等待，最终超过等待时间并产生 timeout。

准确表达：

> 不是简单地认为 Gemini API 不稳定，而是长时间模型处理与同步 HTTP 生命周期不匹配。

### 3. 第二轮尝试：固定每个请求的 MR 数量

限制一个请求最多包含固定数量的 MR。

问题是 MR 的大小差异很大。相同数量的 MR 可能对应完全不同的 token 规模，因此固定数量无法稳定控制请求大小，也无法可靠避免 timeout。

### 4. 第三轮尝试：按照 token 上限动态分组

改为估算每个 MR 的 token 数，并按照一个请求的 token 上限动态决定分组数量。

这比固定 MR 数量更合理，但仍存在两个问题：

- 如果单个 MR 自身已经超过 token 上限，就无法通过普通分组解决。
- 多个 MR 共用一个分析上下文，可能发生上下文相互影响，不利于保持分析隔离。

### 5. 技术调查：发现 Batch API

在调查 Gemini 官方资料时发现 Batch API。它采用异步方式：提交任务后不立即等待结果，而是之后检查处理状态并取得结果。

它与当前业务匹配的原因：

- 已完成 MR 的内容和分析结果基本稳定，可以提前计算并复用。
- 长时间模型处理不再占用一条同步 HTTP 连接。
- 每个 MR 可以保持为独立的模型分析单元。
- 官方 Batch 单价更低，符合成本优化方向。

## 最终架构决策

> Batch API as the primary path, Standard API as the real-time fallback.

### Primary path

1. 找出还没有保存分析结果的 MR。
2. 将每个 MR 作为独立分析单元提交到 Batch API。
3. 定期检查任务状态。
4. 保存完成的分析结果。
5. 用户发起评价时优先复用已有结果。

### Fallback path

如果用户发起评价时，某个 MR 因时间差或任务失败还没有预分析结果：

1. 使用 Standard API 实时分析该 MR。
2. 取得结果后继续下游评分。
3. 保存结果，避免后续重复分析。

本质上是：

> Offline precomputation + online compensation

## 运行策略

### Initial historical backfill

- 先选择具有代表性的目标项目。
- 对过去约一至两年的历史 MR 进行一次整体预分析。
- 项目的代表性和最终时间范围仍在测试，不应描述为已经固定。

### Weekly incremental analysis

- 计划以每周一次作为初始方案。
- 检查上一周期新增、且尚未分析的 MR。
- 通过 Batch API 完成增量分析并保存结果。
- 根据 fallback 触发率、成本和结果时效性继续调整频率。

## 四个核心权衡

| 维度 | 设计选择 | 当前结论 |
|---|---|---|
| Cost | 大部分任务使用 Batch API，复用已保存结果 | 官方单价更低；实际总成本下降幅度仍在测量 |
| Reliability | 将长时间处理移出同步 HTTP 请求 | 原有 timeout 已在实际测试中消失 |
| Accuracy | 每个 MR 保持一次独立模型分析 | 更利于分析隔离；精度提升仍待实验验证 |
| Availability / Latency | 缺少预分析结果时使用 Standard API | 保证下游评分可以继续，但 fallback 比例仍需监控 |

## 中文面试回答（约 2 分钟）

这个系统需要使用 Gemini 对用户指定时间范围内的多个 Merge Request 进行分析，分析结果还会参与后续评分。最初我们使用 Standard API，通过同步 HTTP 请求等待结果。后来管理层提出了降低 API 成本的要求，所以我开始尝试减少请求次数。

第一种方法是把多个 MR 合并到一个请求中。但是随着 token 数和指令复杂度增加，Gemini 的处理时间变长，最终超过 HTTP 的等待时间并发生 timeout。之后我尝试限制每个请求的 MR 数量，但 MR 的大小差异很大，所以固定数量不能真正控制请求规模。我又改成按照 token 上限动态分组，但如果单个 MR 已经超过上限，这个方案仍然无法处理。另外，把多个 MR 放在同一个上下文中也可能影响分析隔离。

在继续调查官方资料时，我发现了 Batch API。由于已完成 MR 的分析结果基本不会变化，并不需要等到用户操作时才生成，所以我决定提前异步分析并保存结果。最终设计以 Batch API 作为主路径，每个 MR 保持一次独立分析；如果用户选择的 MR 还没有预分析结果，就使用 Standard API 实时处理，保证后续评分可以继续。

改用 Batch API 后，原来由同步等待产生的 HTTP timeout 在实际测试中已经完全消失。Batch API 的官方单价约为 Standard API 的一半，但系统实际总成本降低多少、代表性项目如何选择，以及独立分析是否带来可量化的精度改善，目前仍在验证中。我会把这些设计判断和已验证结果分开说明。

## 30 秒版本

管理层提出降低 Gemini API 成本后，我依次尝试了多 MR 合并、固定 MR 数量和 token 动态分组，但这些方案分别遇到了同步 HTTP timeout、请求规模不可控和超大 MR 等问题。之后我根据 MR 结果可预计算和复用的业务特性，选择 Batch API 作为主路径，并保留 Standard API 处理尚未预分析的实时请求。Batch 化后原有 timeout 已在实际测试中消失；实际总成本和精度改善仍在量化验证。

## 面试时不要混淆的表达

不要说：

> Batch API 让总成本降低了 50%。

应该说：

> Batch API 的官方单价约为 Standard API 的一半，但实际总成本下降幅度仍在测量，因为它还取决于 token 量、重试和 fallback 比例。

不要说：

> 一个 MR 一个请求已经证明精度更高。

应该说：

> 独立分析可以减少不同 MR 之间的上下文影响，因此更有利于维持精度；量化对比仍在进行。

不要说：

> Gemini API 不稳定，所以发生 timeout。

应该说：

> 输入规模和分析复杂度增加后，模型处理时间超过同步 HTTP 请求允许的等待时间，说明当前工作负载与同步调用方式不匹配。

## 可能的追问

### 为什么不继续使用 token-based grouping？

它可以更合理地控制输入规模，但不能解决单个超大 MR，也不能消除多 MR 共用上下文的精度顾虑。更重要的是，业务并不要求所有分析都实时生成，所以异步预计算更符合需求。

### 为什么仍然保留 Standard API？

Batch API 不能保证新 MR 在用户评价前一定完成。如果缺少结果，下游评分无法继续，因此需要 Standard API 提供实时补偿。

### 如何证明节省了成本？

需要记录 Standard 与 Batch 的输入、输出 token、请求数量、失败和重试、fallback 次数，并在具有代表性的项目上比较同一分析范围的总费用。现在仍在进行这项测量。

### 如何验证精度？

应选择覆盖不同大小和类型的 MR，分别使用独立分析与多 MR 合并分析，再根据稳定的评价标准进行人工或基准答案对比。验证完成前只表达设计假设，不宣称精度已经提高。

### 为什么是一周一次？

每周一次是当前计划的初始值，不是已经证明的最佳频率。后续要根据 MR 新增速度、用户评价时间、fallback 触发率和运行成本调整。

- `Batch APIにより総コストを50%削減しました` ではなく、`公式単価はStandard APIの約半分ですが、実際の総コスト削減幅は現在測定中です` と説明する。
