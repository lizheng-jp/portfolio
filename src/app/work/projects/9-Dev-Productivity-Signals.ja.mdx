## 実装内容

Dev Productivity Signals は、開発活動を指標と追跡可能な根拠から分析するための個人プロジェクトです。Spring Boot API と Next.js の画面でプロジェクト指標を計算・表示し、別の Python サービスで選択した GitHub プロジェクトについて質問できます。基本画面には GitLab 形式の合成データを使用します。Signals Agent の実プロジェクト経路には GitHub の認証情報と手動で作成した資料インデックスが必要です。

## Applied AI の構成

1. Signals Agent は API Tool を介して、プロジェクト指標、期間比較、メンバー指標、PR のメタデータ、マージ所要時間の分布を取得します。PostgreSQL を直接参照しません。
2. 理由を説明する質問では、プロジェクト・ブランチごとの Qdrant インデックスから PR の説明・議論、Issue の説明と一部のコメントを検索します。意味検索には Gemini またはローカルの Embedding モデルを利用します。ソースコード、保存済み AI 分析、生産性スコアは索引対象外です。
3. Gemini に構造化された Tool の結果と検索資料を渡します。元の GitHub URL を引用し、測定値と解釈を分けるよう指示しています。1 回の質問は最大 5 回の Tool 呼び出し、6 回のモデル応答、240 秒に制限します。

検索処理は回答を生成せず、根拠資料を返します。弱い一致や資料の不完全な収集を検出し、原因を確認できない場合はその限界を示します。インデックスの更新は手動で、通常の質問時には保存済み資料だけを検索します。取得件数にも上限があり、索引済みでも全資料の網羅は保証しません。

## 設計判断と検証状況

- **信頼性・応答時間：** Agent は Compose の任意プロファイルで、Spring 側の機能フラグと内部キーを使います。Prometheus/Grafana で失敗率、リクエストと Tool の P95 時間を観測できます。公開済みの改善実績を示す数値ではありません。
- **コスト：** 差分インデックス更新で変更のない Embedding を再利用し、GitHub の取得件数を制限します。Tool とモデルの呼び出しにも上限を設けました。`gemini-3.8-flash` では 1 回の質問に約 0.02 米ドルかかるため、公開デモの質問はクライアントごとに 1 時間 10 件、全体で 1 日 200 件までとし、同時に処理するのは 1 件だけです。Signals Agent 全体の費用削減率は未計測です。
- **評価：** 単体テストと 5 件の回帰確認用の質問に加え、2026 年 10 月に実プロジェクトで検索と回答を測定しました。方法・結果・限界は次の節にまとめています。
- **デプロイ：** Docker Compose と GitHub Actions に AWS Lightsail へのデプロイ設定があります。Agent と Qdrant はリソース上限付きの任意サービスです。2026 年 10 月 11 日から、公開デモは次の節の評価で選んだ構成（`gemini-3.8-flash`、新しい Tool 方針、根拠のみに基づく回答）で動いており、同日の実際の質問で回答を確認しました。

## 評価結果（2026 年 10 月）

`prometheus/prometheus` の 2026 年 7 月 11 日から 10 月 8 日までの議論（PR 40 件・Issue 10 件、索引済み資料 123 件）を対象に、検索と回答の 2 層で Agent を評価しました。質問は 55 件で、いずれも議論の内容を調べる質問です。35 件は資料に答えがあり（20 件は言い換え、15 件は資料の用語を使用）、20 件は答えがありません（うち 8 件は索引済みの話題に近い質問）。

**正解データ：** 関連資料と参照回答は、Claude と OpenAI Codex がそれぞれ独立に作成しました。Codex には順序を入れ替えた質問、資料本文、作成ルールだけを渡しています。質問と資料の関連判定の一致度は Cohen's kappa 0.87 で、答えられる質問かどうかの判定は全件一致しました。不一致の 15 件は作成ルールに基づいて確定しました。答えのある質問には、正しい回答が含むべき要点を 2〜4 個（計 91 個）定めています。

**検索**（ローカルの `bge-base-en-v1.5`、上位 8 件、PR・Issue ごとに最大 2 件）：

| 指標 | 結果 |
|---|---|
| Recall@3 | 0.84（95% ブートストラップ信頼区間 0.75〜0.92） |
| MRR | 0.89（ランダムな順位付けでは 0.04） |
| 上位 3 件に正しい PR・Issue が含まれる割合 | 0.97 |
| Qwen3-Embedding-0.6B と bge-base の MRR 差 | +0.02（信頼区間 -0.07〜+0.11）。有意な差はなく、CPU では約 40 倍遅い |

**回答**（`gemini-3.8-flash`、同じ 55 件）。資料検索の前に指標取得を必須とし、各 Tool を 1 回までに制限していた従来の方針と、最初から検索でき、別の検索語で再検索もできる新しい方針を比較しました。

| 指標 | 従来の方針 | 新しい方針 |
|---|---|---|
| 答えのある質問に回答できた件数 | 3 / 35 | 21 / 35 |
| 要点の再現率（35 件全体、回答なしは 0） | 0.02 | 0.50（信頼区間 0.35〜0.65） |
| 要点の再現率（回答できた分のみ） | 0.25 | 0.83 |
| 答えのない質問で根拠不足と答えた件数 | 回答 3 件中 1 件 | 回答 15 件中 9 件 |

採点はどちらの方針の回答かを伏せて Codex が行い、私も 15 件を独立に採点しました。要点を述べているかどうか、根拠不足と答えたかどうかの判定はすべて一致しました。一方、根拠のない記述の判定は一致しませんでした。原因は、Agent が GitHub の Tool から取得した PR のメタデータを採点資料に含めていなかったことです。抽出して確認したメタデータは GitHub と一致したため、根拠のない記述には数えていません。今回の Gemini の利用料は約 1.3 米ドルです。

**評価で分かったこと：**

- モデルの変更よりも、独立した 2 人目の作成者の効果が大きくなりました。最初の正解データは、質問や催促だけのコメントを関連資料に含め、長い資料の奥にある答えを見落としていました。修正後、Recall@3 は 0.76 から 0.84 に上がり、順位付けの問題に見えていたものが解消しました。
- Gemini の Embedding 向けに設定した根拠不足の閾値 0.40 は、無関係な資料でもスコアが 0.6 前後になる bge では、答えのない 20 件を 1 件も検出できませんでした。現在は Embedding モデルごとに閾値を設定しています。
- インデックスは最近更新された項目の先頭ページだけを取得していたため、123 件中 66 件が期間最後の 8 日間に偏っていました。現在は作成月ごとに期間全体から抽出します。
- 新しいモデルでは、従来の Tool の制限によって 55 件中 49 件がエラーで終わりました。新しい方針でも 19 件は失敗し（11 件は 5 回の呼び出し上限を超過、5 件は同じ Tool の再呼び出し）、答えのない 15 件中 8 件では資料にない一般知識を付け加え、1 件は資料と矛盾しました。下の第 2 ラウンドでこの 2 点に対応しました。

**第 2 ラウンド：失敗せずに答え、根拠がなければ答えない。** 2 つの変更を 1 つずつ加えました。1 つ目は、Tool の制限をエラーではなくフィードバックにすることです。上限超過や重複した呼び出しには、エラー内容または前回の結果を Tool の応答として返し、モデルは手元の根拠で回答します。2 つ目は、根拠の不足を一般知識で補わないよう指示することです。3 つの構成の回答をまとめ、構成を伏せたうえで同じ基準で採点し、回答に出てくる PR の GitHub メタデータも採点資料に加えました。私が 15 件を独立に採点した結果、要点と回答拒否の判定はすべて一致し、根拠のない記述の判定は 15 件中 12 件で一致しました。

| 指標 | 新しい方針 | ＋フィードバック | ＋根拠のみ |
|---|---|---|---|
| 答えのある質問に回答できた件数 | 21 / 35 | 33 / 35 | 33 / 35 |
| 要点の再現率（35 件全体） | 0.49 | 0.76 | 0.76 |
| 答えのない質問で根拠不足と答えた件数（20 件中） | 7 | 12 | 18 |
| 答えのない質問で一般知識を付け加えた回答 | 15 件中 9 | 20 件中 10 | 19 件中 2 |
| 答えのある質問を誤って拒否した件数 | 0 | 0 | 1 |

フィードバック化により要点の再現率は 0.27 上がりました（対応のある 95% 信頼区間 0.13〜0.41）。根拠のみの指示は再現率を変えず（信頼区間 -0.06〜+0.05）、答えのない質問での一般知識の付け加えを減らしましたが、誤った拒否が 1 件生じました。答えのある質問への回答の約 3 分の 1 は、解釈や推奨の部分にまだ一般知識を含んでおり、これが次の改善対象です。このラウンドのモデル利用料は約 2.5 米ドルです。

**本来の用途：「この指標はなぜ変わったのか」。** 上の評価は検索型の質問で、Agent が本来答えるべき質問ではありません。そこで本番構成に対して 18 件の質問を作りました。通常の変化 10 件、前提が誤っている質問 5 件（実際は増えたコミット数について「なぜ減ったか」と聞くなど）、あり得ない値についての質問 2 件（数年に及ぶバグ修正リードタイムの平均）、ほぼ変化のない指標 1 件です。参照回答がないため、各回答が実際に受け取った Tool の結果と照らして性質を検査しました。Tool の結果は評価用リクエストだけが指定できる trace 項目で記録しています。数値と引用はプログラムで検査し、言語面は Codex が採点しました。私は先に 10 件を独立に採点し、判定が分かれた点はすべて完全な記録と照合して確定しました。

| 検査 | 結果 |
|---|---|
| 回答中の数値が根拠に含まれる、または根拠から計算できる | 404 / 404 |
| 引用した PR・Issue が根拠に含まれる | 全件 |
| 変化の方向が正しい | 18 / 18 |
| 誤った前提を訂正した | 5 / 5 |
| 根拠のない原因の断定 | 0 / 18 |
| 根拠の限界を明記した | 17 / 18 |
| あり得ない値を疑った | 0 / 2 |

Agent は測定された変化を正確に伝え、原因をでっち上げることはありません。ただし、あり得ない値を疑うことは一度もなく、数年に及ぶバグ修正リードタイムを「長期間かかった少数の修正」として説明しました。これはプロンプトではなく、Tool の出力に妥当性チェックを加えて対処すべき問題です。判定を確定する過程で、採点資料が根拠を 1,500 文字で切っていたため、根拠のある 2 つの数値が捏造に見えていたという自分の側の不備も見つかりました。18 件は動作確認の規模で、0 / 18 でも実際の発生率が約 17% である可能性は残ります。

質問、正解データ、回答、採点結果、スクリプトはリポジトリにあります：[eval/README.md](https://github.com/lizheng-jp/dev-productivity-signals/blob/main/eval/README.md)。

**限界：** 対象は 1 リポジトリのみで、資料を読んだ後に作成した 55 件の調査型の質問と、本来の用途についての 18 件の質問です。モデルごとの閾値は同じ質問で選んだため、その数値は楽観的です。採点者は相互に照合した言語モデルであり、領域の専門家ではありません。本番環境の検索は、ここで評価したローカルモデルではなく Gemini の Embedding を使います。

この実装では、AI の説明を測定値、追跡できる資料、不確実性とともに示すことを重視しました。GitHub 上の議論は指標変化の手掛かりになりますが、それだけで因果関係は確定できません。
